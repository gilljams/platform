Why register dimensions?
The platform needs to know which dimensions exist to correctly route and enrich data. Each dimension has an owner (often ERP) that owns the canonical code list, producers that send data and consumers that receive it.
Shared Taxonomy (technical)
shared_dimensions (name PK, label, owner_system, taxonomy_type)
dimension_codes (dimension_name, code, label)
dimension_participants (dimension_name, product, role, uses_canonical)
dimension_code_mappings (dimension_name, product, local_code, canonical_code)

Scaling: N+M mappings (N producers + M consumers), not N×M
Normally set at customer installation, updated when chart of accounts changes.

Example: "Nybyggen AB"
The customer has the ERP fields activity, cost_bearer and counterpart on each journal entry line. The budget tool has the same fields. We configure:
• dim1 = Activity (from both ERP's and budget's activity field)
• dim2 = Cost Center (from cost_bearer)
• dim3 = Counterpart (from counterpart)
Now the platform knows that each GL line and budget line should be enriched with these three values.
Approach C — named core + generic flex (technical)
dim_models: prod_b.dim1="Activity", dim2="Cost Center", dim3="Counterpart"
dim_routing: erp.activity→dim1, erp.cost_bearer→dim2, erp.counterpart→dim3
             prod_a.activity→dim1, prod_a.cost_bearer→dim2, prod_a.counterpart→dim3

GL ingress  → applyDimRouting("erp","prod_b",entry)   → dim_values_per_entry
Budget out  → applyDimRouting("prod_a","prod_b",line)  → dim_values_per_line
→ Product B stores dim1/dim2/dim3 for BOTH budget and actuals

Configured once at customer installation.
Can be extended if the customer adds more source fields.

What is this?
When ERP or Product A creates a new project it automatically appears here with a "canonical ID". The status shows if the project only exists in one system (unlinked) or if it's connected in both (linked).
ID Mapping (technical)
canonical_projects (canonical_id PK)
id_mappings (source_system, source_id ? canonical_id)

Automatiskt vid ProjectCreated/BudgetProjectCreated events.
Manual linking: POST /api/link → merge canonical_id

Link Projects

Manual step — link ERP project to budget project

ERP and Product A create projects independently. Here they are linked so that the platform knows it's the same physical project. Afterwards Product B can show budget + actuals in the same view.

What is Demo Runner?
Simulates a full customer flow step by step. Step 1 performs the initial setup automatically (dimensions + economic model). Then come operational flows (projects, budgets, actuals). All tabs update live as steps progress.
Demo Runner API (technical)
POST /api/demo/step/1  → Initial Setup: reference data + economic model + dimension catalog
POST /api/demo/step/2  → ERP: create project
POST /api/demo/step/3  → ERP: publish GL (with flex-dims)
POST /api/demo/step/4  → Product A: create budget project
POST /api/demo/step/5  → Product A: save budget (draft)
POST /api/demo/step/6  → Platform: planning dimension mapping
POST /api/demo/step/7  → Product A: submit budget
POST /api/demo/step/8  → Platform: link projects
POST /api/demo/step/9  → Product B: show analytics
