Why register dimensions?
The platform needs to know which dimensions exist to correctly route and enrich data. Each dimension has an owner (often ERP) that owns the canonical code list, producers that send data and consumers that receive it.
Cross-reference mappings (code mappings)
Each connected system's local code for a dimension member is registered as a cross-reference mapping to the canonical code. This enables the platform to translate between systems.

Automatic: When the platform routes reference data (e.g. AccountsPublished), the router auto-registers code mappings for all dimension participants — both producers and consumers. The source system (ERP) gets a source_key as authoritative reference ID.

Product-specific local codes: When a product uses its own internal codes that differ from canonical (e.g. Product A uses BUD-4010 instead of 4010), the product registers these back via the platform API. In this POC, Product A's local codes are seeded in demo step 1 as a shortcut — in production each product would call POST /api/shared-dimensions/:name/mappings to register its own codes.
Shared Taxonomy (technical)
shared_dimensions (name PK, label, owner_system, taxonomy_type)
dimension_codes (dimension_name, code, label)  — delegates to econ_entities
dimension_participants (dimension_name, product, role, uses_canonical)
dimension_code_mappings (dimension_name, product, local_code, canonical_code, source_key)

Code mapping flow:
  1. ERP publishes AccountsPublished → Kafka
  2. Platform Router forwards to platform.accounts.out
  3. Router auto-registers mappings for ALL participants:
     - ERP (producer): local_code=code, source_key=ERP-ACC-001...
     - Product A/B (consumers): local_code=canonical_code (passthrough)
  4. Products with own codes register via API (or demo seeding)

Scaling: N+M mappings (N producers + M consumers), not N×M
Normally set at customer installation, updated when chart of accounts changes.

Example: "Nybyggen AB"
The customer's ERP sends fields activity, cost_bearer and counterpart on each journal entry line. The platform stores these values in generic dim-slots (dim1, dim2, dim3). We configure routing to tell the platform which ERP field maps to which slot:
• erp.activity → dim1 (product labels it "Activity")
• erp.cost_bearer → dim2 (product labels it "Cost Center")
• erp.counterpart → dim3 (product labels it "Counterpart")
Now all GL lines and budget lines use the same dim1/dim2/dim3 regardless of source.
Architecture — named core + generic flex slots
dim_models (per product):
  prod_a.dim1 = "Activity", dim2 = "Cost Center", dim3 = "Counterpart"
  prod_b.dim1 = "Activity", dim2 = "Cost Center", dim3 = "Counterpart"

dim_routing (source_field → target_slot):
  erp.activity → dim1, erp.cost_bearer → dim2, erp.counterpart → dim3
  prod_a.dim1 → dim1, prod_a.dim2 → dim2, prod_a.dim3 → dim3

econ_entities: stores flex dim codes under dim1, dim2, dim3
econ_facts:    stores values in dim1, dim2, dim3 columns

Flow:
  ERP GL entry { activity: "AKT-100" }
    → econ_facts.dim1 = "AKT-100"
    → applyDimRouting("erp", "prod_b", {activity:"AKT-100"}) → {dim1:"AKT-100"}
    → Product B receives dim1 = "AKT-100", knows dim1 = "Activity"

Overview — Domain Pipeline

This tab shows the operational pipeline for the selected domain. The platform provides a source-agnostic staging layer per domain — the adapter reads source data, transforms it into a standard format, and publishes it via Kafka. Products never talk to source systems directly.

ERP (source)                        Platform                                Products
───────────                     ────────────────                        ─────────────
 accounts  ──► Adapter ──► econ_entities ──► Structural Policies ──►  DimensionSnapshot ──► dim_members
 org_units         │        econ_relations    (auto_root, grouping)     (Kafka event)        dim_relations
 GL entries        │        econ_facts ──► validate ──► publish ──►   GL/Budget events ──► gl_lines
                   │        econ_attribute_defs                                              budget_lines
                   └──────► econ_entity_attributes ──► Publish Rules ──► (attributes in snapshot)

Each section on this page represents a stage in this pipeline. Together they control how data flows from source to products.

Pipeline Summary

Shows counters for the staging layer: how many entities (accounts, org units, etc.), relations (hierarchies), and facts (GL transactions) are currently staged. Facts pass through three states:

received → validated → published

A fact that fails validation becomes rejected and needs manual review.

Actions

Validate pending facts — runs validation rules on all received facts (e.g. account code exists, amount is numeric). Valid facts move to validated; invalid ones become rejected.

Publish validated — publishes all validated facts to Kafka (platform.gl.out). Products consume these events and store into their local gl_lines tables.

Full sync (ERP) — triggers a complete sync cycle: fetch entities + facts from ERP, apply structural policies, publish dimension snapshots, and stage GL transactions.

Sync periods — re-reads GL data for a specific period range from the ERP, bypassing the high watermark. Old staged data for those periods is deleted and replaced with fresh data. Use this when source data has been corrected retroactively.

Entities

Browse all entities staged in the Economy Domain, filterable by dimension (account, org_unit, project, etc.). Entities are the building blocks that appear in dimension hierarchies and that transactions reference. They arrive from the ERP adapter during sync and are the input for Structural Policies.

Sync State & Scheduler

Sync State shows per-source status: when the last sync ran, how many rows were received/validated/rejected.

Scheduler lets you set a cron expression for automatic periodic syncs. The schedule runs inside the Platform container.

0 2 * * *Every night at 02:00
*/15 * * * *Every 15 minutes
0 8 * * 1-5Weekdays at 08:00

The schedule persists until stopped or the container restarts. You can always trigger a manual sync regardless of the schedule.

Structural Policies

Rules that shape dimension hierarchies after adapter sync but before products receive the data. They ensure consistent structures without modifying the original source data.

Auto Root Creates a _ALL root node and connects all leaf entities as children. Gives every dimension a single entry point for drill-down.
Auto Missing Creates a _MISSING node under the root. Transactions referencing unknown codes can be caught here instead of being lost.
Grouping Rules Creates intermediate group nodes based on patterns (first N characters, character range, or regex). E.g. accounts 3010–3030 grouped under a "30" node.

Execution order: Auto Root → Auto Missing → Grouping Rules (per dimension).
When applied: Automatically after each ERP sync, or manually via "Apply All".

Attribute Publishing

Controls which member attributes are included in DimensionSnapshot events sent to products. Attributes originate from the ERP (e.g. account_type, region) and are discovered automatically during sync via the ERP's self-describing capabilities API.

Three modes:

Passthrough No rules configured for a dimension — all attributes are published as-is with their original names and values. This is the default.
Published (with rule) A rule maps source_attribute → publish_as. Optionally includes a value mapping (JSON) to translate values, e.g. {"income":"I","expense":"K"}.
Not published When rules exist for a dimension, any attribute without a rule is excluded from the snapshot. This lets you filter out irrelevant attributes.

Click Republish after changing rules to re-send dimension snapshots immediately.

Example — from ERP attribute to product behavior

A concrete example of how attributes flow through the layers:

1. ERP declares that accounts have an attribute account_type with values like "income" or "expense".
   Account 3010 (Sales revenue) has account_type = "income".
   Account 4010 (Salaries) has account_type = "expense".

2. Platform discovers this during sync and stores it in the Economy Domain.
   An admin creates a publish rule:
     account_type → publish as "kontoklass", values: {"income":"I", "expense":"K"}

3. DimensionSnapshot (Kafka event) now includes:
   { code: "3010", name: "Sales revenue", attributes: { kontoklass: "I" } }
   { code: "4010", name: "Salaries",      attributes: { kontoklass: "K" } }

4. Product B receives and stores these attributes locally.
   The product admin creates an ingestion rule:
     "If member_attr:account:kontoklass = I → set dim2 = REVENUE"
     "If member_attr:account:kontoklass = K → set dim2 = COST"
   Now every GL line is auto-tagged with a cost/revenue category for reporting.

Another example: an org_unit attribute region could let a product group organizational units by geographic area, or a level attribute could control which org units appear in summary reports. The platform provides the building blocks; each product decides what to do with them.

Fact Pipeline — GL data ingestion

GL (General Ledger) transactions flow from ERP to products through a three-layer idempotent pipeline. The design prevents duplicates on re-sync, supports period-based re-reads, and uses high-watermark tracking for incremental sync.

Layer Mechanism Dedup strategy
ERP (source) Pull-based API: GET /api/gl with period_from, period_to, modified_since params. Each row has a deterministic entry_id (e.g. gl-3010-OU-100-2025-01) and modified_at timestamp.
Platform (staging) econ_facts table with UNIQUE(source_system, source_row_id). Insert uses ON CONFLICT DO UPDATE (upsert). Same row from same source always overwrites — never duplicated. Period re-syncs delete old period data first then re-insert.
Product (consumer) Reads sync_mode from Kafka event. When replace_by_period: deletes gl_lines for those periods before inserting. Period-level atomicity: old data removed, new data inserted. No stale or duplicated rows.

Sync modes:

Incremental (default) Uses high_watermark (last modified_at seen). Only fetches rows modified after the watermark. Fast, minimal data transfer.
Period re-read Admin specifies period_from / period_to. Ignores watermark, fetches all rows for those periods, deletes old staged data for those periods, and re-inserts. Useful when source data has been corrected retroactively.
Full sync No period filter, no watermark. Fetches everything. Upsert ensures no duplicates. Safe to run as a "reset" but slower.

The high watermark (shown in the Sync State table) tracks the latest modified_at timestamp from the ERP. On each incremental sync, only rows newer than this value are fetched. After a successful sync, the watermark advances to the newest timestamp in the batch.

Layer model — who owns what?

The architecture has a clear separation of responsibilities. Each layer owns its own logic and never reaches into another layer's domain:

Layer Responsibility Examples
ERP (source) Owns the master data. Declares what attributes exist and what values each member has. Accounts, org units, hierarchies, GL transactions, account_type, region
Platform Standardizes, curates, and distributes. Transforms source data into a common format, applies structural policies, controls which attributes reach products and in what shape. Does not contain product-specific business logic. Adapter mapping, auto_root, grouping rules, attribute publish rules (rename/remap/filter), dim routing
Product Owns its business logic. Receives curated data from the platform and decides how to use it — grouping dimensions, deriving categories, setting defaults, building reports. Does not know about the ERP or how data was sourced. Ingestion rules (derive dim2 from kontoklass), local dimension groupings, budget validation, report aggregation

Key principle: The platform gives products capabilities (attributes, hierarchies, curated data) — but the decision of how to use them lives in the product. This means the same attribute (e.g. kontoklass) can drive completely different behavior in different products: one product might use it for report grouping, another for access control, a third might ignore it entirely.

Pipeline Configuration — Error Policy & Auto-Publish

Controls what happens after validation when some rows fail. This is inspired by enterprise ETL patterns (Snowflake ON_ERROR, dbt store_failures, Fivetran connector error handling).

Policy Behavior Use when
skip_invalid Publish all valid rows. Rejected rows are logged but do not block. Default. Source data is mostly correct; a few missing codes are acceptable.
abort_on_error Block publish entirely if ≥1 row is rejected. Status becomes blocked. Critical financial data. No partial data is acceptable.
threshold:N Block publish if rejection rate exceeds N%. E.g. threshold:10 blocks if >10% rejected. Tolerant of occasional errors but wants a safety net for large-scale source issues.

Auto-publish: When enabled, the sync runner automatically publishes validated facts to downstream products immediately after validation — provided the error policy allows it. This eliminates the manual "Validate → Publish" workflow.

Manual workflow (auto-publish off):
  Run Sync → [facts staged] → Click Validate → [validated/rejected] → Click Publish → [sent to Kafka]

Automated workflow (auto-publish on):
  Run Sync (or scheduled cron) → stage → validate → policy check → publish ✓
  If policy blocks: status = "blocked", admin investigates rejected rows.

Rejection reason: Each rejected row now stores the specific validation error (e.g. "unknown account '9999'") making it easy to diagnose and fix issues at the source.

Rejected Facts (error visibility)

When facts fail validation, they move to rejected status with a reason stored per row. The Rejected Facts panel below exposes these errors directly in the UI so you can:

  • See exactly which rows failed and why
  • Identify if the problem is at the source (missing account in ERP) or in configuration (dimension not synced)
  • Decide whether to fix the source and re-sync, or accept and move on

This follows the Observability principle from modern data engineering: errors should be visible, searchable, and actionable — not hidden in log files.

How it all connects (end-to-end)
1. Sync         ERP adapter fetches accounts, org_units, GL → stages in econ_* tables
                Attributes discovered from ERP capabilities → econ_attribute_defs + econ_entity_attributes
                GL entries pulled via GET /api/gl with period filtering or high watermark (modified_since)
2. Policies     Structural policies add _ALL root, grouping nodes, _MISSING
3. Attributes   Publish rules rename/remap/filter attributes before they leave the platform
4. Facts        GL transactions upserted via UNIQUE(source_system, source_row_id) — idempotent
                Period re-syncs delete + replace; incremental syncs advance the high watermark
5. Publish      DimensionSnapshot (entities + relations + attributes) → Kafka
                GL facts validated → published (with sync_mode + periods) → Kafka
6. Products     Consume snapshots → local dim_members + dim_relations + dim_member_attributes
                Consume GL/Budget → period-based replace or append → apply ingestion rules → store

Key insight:
  The platform provides the building blocks — products decide how to use them.
  Three-layer idempotency (ERP entry_id, Platform upsert, Product replace-by-period)
  ensures that re-syncing is always safe and never causes duplicates.

SCIM 2.0 Protocol — what this section simulates

This form is a simulator. It lets you manually trigger SCIM API calls to test the provisioning endpoint — exactly the same calls that an Identity Provider (Microsoft Entra ID, Okta, Zitadel) would make automatically in production.

In production, this form does not exist. Instead, the IdP is configured with the SCIM endpoint URL (POST /api/scim/v2/Users) and a bearer token. Whenever a user is created, updated, or deactivated in the IdP, it automatically pushes the change to the platform — no human interaction needed.

Users provisioned via SCIM get source: "scim" and an external_id matching the IdP's object ID. They do not get a password here — in production they authenticate at the IdP via OIDC/SAML, not with a local password. 

Provisioning (IdP → Platform):
  POST /api/scim/v2/Users
  {
    "schemas": ["urn:ietf:params:scim:schemas:core:2.0:User"],
    "externalId": "azure-abc-123",
    "userName": "new.user",
    "displayName": "New User",
    "emails": [{ "value": "new@example.com", "primary": true }],
    "groups": [
      { "display": "role:editor" },
      { "display": "product:prod_a" },
      { "display": "product:prod_b" },
      { "display": "org:OU-100" },
      { "display": "controllers" }
    ],
    "active": true
  }

Group claim mapping (automatic):
  "role:X"    → sets role = X
  "product:X" → adds X to products list (first = primary)
  "org:X"     → sets org_unit = X
  other       → stored as plain group name

Update (IdP → Platform):
  PATCH /api/scim/v2/Users/:externalId
  {
    "schemas": ["urn:ietf:params:scim:api:messages:2.0:PatchOp"],
    "Operations": [
      { "op": "replace", "path": "displayName", "value": "Updated Name" },
      { "op": "replace", "path": "active", "value": false }
    ]
  }

Deprovision (IdP → Platform):
  DELETE /api/scim/v2/Users/:externalId
  → Soft-delete: sets status = "deprovisioned"
  → User can no longer log in but audit trail is preserved

JWT Token (what it contains)
The platform issues a JWT with these claims:
{
  "user_id": "user-001",      // ← sub claim in OIDC
  "name": "Anna Svensson",    // ← from SCIM displayName
  "role": "controller",       // ← mapped from IdP group
  "org_unit": "OU-100",       // ← platform attribute
  "products": ["prod_a"],     // ← platform entitlement
  "primary_product": "prod_a" // ← platform attribute
}

In production:
- Claims come from the IdP's id_token
- Platform can enrich with local attributes (products, org)
- Products validate the token signature (shared secret / JWKS)
- Token expiry: 8h (configurable)

Architecture Vision

The foundational thinking behind this POC and the platform model it explores.

Core Philosophy

A loosely coupled, event-driven platform model where shared cross-product capabilities are centralized in a platform layer, while individual products remain autonomous, independently deployable, and free to evolve their own internal models.

The Platform Layer

The platform centralizes capabilities that would otherwise be duplicated across products:

Identity & Access
Centralized user lifecycle, SSO, SCIM provisioning, and role-based access across all products.
Master Data & Mappings
Shared entity registry and canonical ID mappings. Each product keeps its own identifiers, the platform bridges them.
Integration Layer
Unified interface toward external domains and source systems (ERP, HR, CRM). Normalizes data into consistent domain models.
Event-Driven APIs
Ingress/egress event bus for asynchronous communication. Products subscribe to domain events rather than calling each other.
Observability & Governance
Shared tracing, audit logging, configuration management, and operational monitoring across the product portfolio.
Shared UX Shell
Injected navigation, inbox, and branding that creates a unified experience across independent product frontends.

Domain-Oriented Integration

The platform acts as a unified interaction layer toward domains such as Finance, HR, and CRM. Data originating from multiple upstream systems is normalized and exposed through consistent domain-oriented models and contracts.

External domains remain systems of record and publish business entities and events into the platform. Products consume these events, maintain their own internal identifiers and relations, and stay decoupled from each other through shared contracts and event-driven communication.

Data flow
ERP / HR / CRM  →  Platform (normalize + route)  →  Product A, Product B, ...
Product A  →  Platform (event bus)  →  Product B

Product Autonomy

Each product in the portfolio is a self-contained unit with its own:

  • Database and data model — no shared schemas between products.
  • Technology stack — free to choose frameworks, languages, and storage.
  • Deployment lifecycle — independent releases, scaling, and versioning.
  • Internal identifiers — products don't need to know each other's IDs. The platform provides entity mapping.

Products communicate exclusively through the platform's event bus and shared contracts — never through direct database access or synchronous inter-product calls.

What This Approach Enables

✔ Strong domain ownership — each team owns its product's data and logic completely.
✔ Scalable integrations — new source systems added at the platform level, not per product.
✔ Loose coupling — products evolve independently without breaking each other.
✔ Easier onboarding — new products integrate via standard event contracts, not custom APIs.
✔ Consistent data handling — cross-domain mappings managed centrally, not scattered across products.
✔ Independent evolution — products and integrations evolve on their own timelines.

POC Scope

This proof of concept implements a vertical slice through the architecture to validate the model end-to-end:

  • 7 Docker containers — platform, 2 products, Kafka (Redpanda), console, Jaeger, ERP mock.
  • Event-driven data flow — ERP publishes projects/accounts → platform routes to products via Kafka.
  • Shared shell — injected header with navigation, and pin/unpin across all products.
  • Platform services — shared capabilities delivered through the shell: master inbox, AI assistant, external tool links.
  • SCIM provisioning — automated user lifecycle from IdP with group-to-role mapping.
  • Budget workflow — full create → edit → submit → publish → cross-product sync lifecycle.
  • Process management — assignment matrix, task inbox, status tracking.
  • External tools — configurable third-party links in the unified navigation.

Production Notes

Shortcuts taken in this POC and considerations for a real deployment.

Multi-tenancy

POC: Single-tenant — one database, one Kafka cluster, no tenant isolation.

Production approach: The platform layer (shell, router, SCIM gateway) can be shared across tenants since it's largely stateless. Key requirements:

  • Tenant-ID propagation — every request carries a tenant identifier (JWT claim or header), validated at the gateway. Misssing this on a single query = data leak.
  • Kafka topic isolation — prefix all topics with tenant ID (tenant-a.projects.in) and enforce ACLs so consumers only read their own topics.
  • Config DB — shared database with a tenant_id column + Row-Level Security (Postgres RLS) so the app can never accidentally cross tenants.
  • Product instances — always per-tenant (separate pods/DBs). This is already how the POC works with isolated containers.
  • Dedicated tenant option — some customers (banking, healthcare) require fully isolated infrastructure. Support this as a deployment variant using the same codebase.

Authentication & Authorization

POC: Simplified login with plaintext passwords in SQLite. SCIM provisioning works but tokens aren't validated cryptographically.

  • Real SSO — OpenID Connect with the customer's IdP (Entra ID, Okta, etc.). Platform issues a signed JWT after IdP authentication.
  • Token validation — products validate JWT signature via JWKS endpoint. No shared secrets in environment variables.
  • SCIM bearer tokens — should be rotatable, scoped per tenant, stored hashed.
  • Session management — token refresh, expiry handling, secure cookie flags (HttpOnly, SameSite, Secure).
  • RBAC enforcement — the POC has roles but doesn't enforce them in product APIs. Production needs middleware that checks role claims on every endpoint.

Data & Event Pipeline

POC: Redpanda single-node, no replication, no persistence across restarts. Events are JSON with basic schema.

  • Schema registry — enforce event schemas (Avro/Protobuf) so producers can't send malformed data. Breaking changes require schema evolution.
  • Dead letter queues — failed events should go to a DLQ for inspection, not be silently dropped.
  • Delivery guarantees — the POC uses at-least-once with idempotency keys. Production should formalize this with transactional producers and exactly-once semantics where critical.
  • Backpressure & rate limiting — protect downstream products from event floods (noisy neighbor problem).
  • Event versioning — events need a version field and consumers must handle old versions gracefully.

Shell & Micro-frontend Architecture

POC: Shell injected via <script> tag. Products are separate HTML apps loaded in full-page navigations.

  • Module federation — consider Webpack Module Federation or import maps for seamless product loading without full-page reloads.
  • Shell versioning — the CDN-served shell.js needs cache-busting and rollback capability. A broken shell breaks all products.
  • CSS isolation — shadow DOM or strict naming conventions to prevent style leaks between products and shell.
  • Cross-product communication — the POC uses page navigation. Production may need a lightweight event bus (postMessage / custom events) for in-page coordination.
  • Performance — shell.js should be < 20KB gzipped. Currently it's small, but monitor as features grow.

Infrastructure & Operations

POC: Docker Compose on a single machine. SQLite in-memory databases. No monitoring, no backups, no TLS.

  • Orchestration — Kubernetes with Helm charts per product. Platform services as a shared namespace, product instances as tenant-scoped namespaces.
  • Database — PostgreSQL (or managed equivalent) with connection pooling, backups, and point-in-time recovery.
  • TLS everywhere — not just ingress; mTLS between services (service mesh like Istio or Linkerd).
  • Observability — the POC has Jaeger for tracing. Add structured logging (ELK/Loki), metrics (Prometheus/Grafana), and alerting.
  • Audit logging — who changed what, when. Required for compliance. Per-tenant audit streams.
  • Secrets management — Vault or cloud KMS for API keys, DB credentials, encryption keys. Not environment variables.

Data Privacy & Compliance

POC: No encryption at rest, no data classification, no retention policies.

  • Encryption at rest — all databases and Kafka logs encrypted. Per-tenant keys (envelope encryption) so one key compromise doesn't affect all tenants.
  • GDPR — right to deletion, data portability, consent tracking. Platform needs a "delete tenant" operation that cascades across all products.
  • Data residency — some customers require data in specific regions. Multi-region deployment support.
  • PII handling — user data (names, emails) must be identified and treated differently from operational data. Minimize PII in event payloads.

Platform Admin: Customer vs Operations

POC: All administration in a single portal. No separation between what the customer's admin does and what the vendor's operations team does.

Production approach: Two distinct admin experiences, potentially role-gated within the same app or as separate portals:

Tenant Admin (customer) Ops Portal (vendor)
Who Customer's own admins Internal operations / SRE team
Scope External tools, users & roles, branding, notifications Tenant provisioning, product setup, data routes, Kafka topics, monitoring
POC tabs External Tools, Identity & Access Initial Setup, Data Operations, Operations, Events
Access Normal login with admin role Separate portal, VPN/IP-restricted, or super-admin role

Implementation options:

  • Role-gated tabs — same admin app, but tabs/sections shown based on role claims. Simplest to build and maintain.
  • Separate portals — distinct deployments for customer admin vs ops. Better security boundary but more to maintain.
  • Hybrid — single codebase, ops-portal deployed on internal network with elevated role scope.

Product Configuration via Platform

Today: Products are configured via YAML files deployed alongside the application. Changing a setting requires a code change, PR, and redeploy.

Opportunity: The platform can serve as a central configuration plane for "moving parts" — settings that change more often than code deploys.

Candidates for platform-managed config:

  • Feature flags — toggle features per tenant without redeploying the product.
  • Display settings — currency format, decimal precision, fiscal year start, language.
  • Data mapping rules — which ERP fields map to which product fields. Already partially in the platform router.
  • Notification templates — email/in-app notification content and triggers.
  • Workflow rules — approval thresholds, budget lock dates, submission deadlines.
  • Integration credentials — API keys for external systems (stored encrypted).

Should stay in YAML / code:

  • Schema definitions — database migrations, event schemas. Too risky to change at runtime.
  • Infrastructure config — resource limits, replica counts, network policies. Managed by IaC (Terraform/Helm).
  • Security policies — CORS origins, CSP headers, auth providers. Change requires deliberate review.

Architecture pattern:

  • Platform exposes a Config API — products fetch their config at startup and poll/subscribe for changes.
  • Config hierarchy — defaults → product-level → tenant-level overrides. Tenant admin can change their tier, ops can change defaults.
  • Audit trail — every config change logged with who, when, old value, new value.
  • Validation — platform validates config against a product-defined JSON schema before accepting changes. Prevents broken configs.
  • Rollback — config versioned so any change can be instantly reverted.

What This POC Validates

  • Shared shell pattern — injected header with navigation, inbox, and pin/unpin works well across independent products.
  • Event-driven data routing — ERP data flows through the platform to multiple products via Kafka with canonical mapping.
  • SCIM provisioning — automated user lifecycle from IdP, including group-to-role mapping.
  • Product independence — each product has its own tech stack, database, and deployment. The platform doesn't dictate internals.
  • External tools integration — lightweight linking to third-party tools in the unified navigation.
  • Admin as a product — platform administration through the same UX patterns as any other product.

Help Service Architecture

The help service is a shared platform capability — all products in the installation share the same article database.

Access model: Each article is tagged with a product (or null for platform-wide). The shell help panel filters articles based on the logged-in user's product access.

Deep linking: Products can open a specific article via shell.openHelp('slug') or by linking to the platform help URL with a slug parameter. This enables inline help buttons in product reports.

Platform Help Service
─────────────────────
  help_articles (slug PK, title, product?, category, body_md, keywords)
  
  API:
    GET  /api/help              — all articles (admin)
    GET  /api/help/user?products=prod_a,prod_b — filtered for user
    GET  /api/help/slug/:slug   — single article by slug (product deep-link)
    POST /api/help              — create article
    PUT  /api/help/:id          — update article
    DELETE /api/help/:id        — delete article

  Shell integration:
    ? icon in shell bar → opens help panel (search + browse)
    shell.openHelp('slug') → opens panel at specific article
    AI chat → uses article content as RAG context
