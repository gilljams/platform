Why register dimensions?
The platform needs to know which dimensions exist to correctly route and enrich data. Each dimension has an owner (often ERP) that owns the canonical code list, producers that send data and consumers that receive it.
Cross-reference mappings (code mappings)
Each connected system's local code for a dimension member is registered as a cross-reference mapping to the canonical code. This enables the platform to translate between systems.

Automatic: When the platform routes reference data (e.g. AccountsPublished), the router auto-registers code mappings for all dimension participants — both producers and consumers. The source system (ERP) gets a source_key as authoritative reference ID.

Product-specific local codes: When a product uses its own internal codes that differ from canonical (e.g. Product A uses BUD-4010 instead of 4010), the product registers these back via the platform API. In this POC, Product A's local codes are seeded in demo step 1 as a shortcut — in production each product would call POST /api/shared-dimensions/:name/mappings to register its own codes.
Shared Taxonomy (technical)
shared_dimensions (name PK, label, owner_system, taxonomy_type)
dimension_codes (dimension_name, code, label)  — delegates to econ_entities
dimension_participants (dimension_name, product, role, uses_canonical)
dimension_code_mappings (dimension_name, product, local_code, canonical_code, source_key)

Code mapping flow:
  1. ERP publishes AccountsPublished → Kafka
  2. Platform Router forwards to platform.accounts.out
  3. Router auto-registers mappings for ALL participants:
     - ERP (producer): local_code=code, source_key=ERP-ACC-001...
     - Product A/B (consumers): local_code=canonical_code (passthrough)
  4. Products with own codes register via API (or demo seeding)

Scaling: N+M mappings (N producers + M consumers), not N×M
Normally set at customer installation, updated when chart of accounts changes.

Data Operations architecture

The Data Operations layer (Economy Domain) is a source-agnostic staging layer that decouples the platform from specific ERP connectors.

Pipeline: External source → econ_entities / econ_facts → validate → publish → Kafka → downstream products.

Tables: econ_entities, econ_entity_attributes, econ_attribute_defs, econ_relations, econ_facts, sync_state.

API: /api/economy/entities, /api/economy/facts, /api/economy/relations, /api/economy/sync-state

Scheduler & cron syntax

The scheduler uses cron expressions to trigger periodic ERP syncs. Format:

┌───── minute (0–59)
│ ┌───── hour (0–23)
│ │ ┌───── day of month (1–31)
│ │ │ ┌───── month (1–12)
│ │ │ │ ┌───── day of week (0–7, 0 and 7 = Sunday)
│ │ │ │ │
* * * * *

Examples:

0 2 * * *Every night at 02:00 (default)
*/15 * * * *Every 15 minutes
0 */6 * * *Every 6 hours
0 8 * * 1-5Weekdays at 08:00
0 6,18 * * *Twice daily at 06:00 and 18:00

How it works: The node-cron library runs inside the Platform container. When the schedule fires it calls POST /api/economy/sync/erp/run, which fetches data from ERP Mock, upserts into econ_entities / econ_facts, validates, and publishes to downstream products via Kafka.

Set schedule: Enter a cron expression and click "Set schedule". The schedule persists until stopped or the container restarts.

Stop: Click "Stop" to cancel the active schedule. You can always trigger a manual sync using the "Manual sync (ERP)" button above.

User Directory — manual user management
This section lets you create and manage users directly in the platform. Use it when you need to add users manually — for example during development, for service accounts, or for customers without a SCIM-compatible Identity Provider.

Users created here get source: "local" and a password you choose. They can log in immediately with the username/password you set.

In production, most users would not be created here — they'd be pushed automatically from an IdP via SCIM (see the section below). But the User Directory always serves as the central read/write view of all users regardless of source.

Source field indicates where the user came from:

Identity architecture (production)
In production, the platform does NOT handle login directly.
Instead, an external Identity Provider (IdP) manages authentication:

┌───────────┐    OIDC/SAML2     ┌──────────┐
│ IdP        │ ◄───────redirect──── │ Platform │
│ (Zitadel/  │ ────id_token+access─► │          │
│  Azure AD) │                │          │
└───────────┘                └──────────┘
      │                          │
      │ SCIM 2.0 sync           │ GET /api/users
      ▼                          ▼
 ┌──────────┐         ┌─────────────┐
 │  users   │ ◄─read─ │ Product A/B │
 │ (SQLite) │         └─────────────┘
 └──────────┘

1. OIDC (OpenID Connect): User logs in at IdP, gets back tokens.
   Platform validates the id_token, never sees the password.

2. SCIM 2.0: IdP pushes user create/update/deactivate to
   POST /api/scim/v2/Users. Platform stores in users table.

3. SAML2: Same as OIDC but with XML assertions. Used by
   enterprise customers (ADFS, Azure AD).a

4. Authorization: Platform stores product entitlements,
   org membership, and role. Products query via API.

In this POC, we simulate the entire flow:
- Users are seeded with demo credentials (source: "local")
- Login is handled directly (no redirect to IdP)
- SCIM endpoint is available but called manually from admin UI
- JWT tokens mirror what an OIDC flow would produce

SCIM 2.0 Protocol — what this section simulates

This form is a simulator. It lets you manually trigger SCIM API calls to test the provisioning endpoint — exactly the same calls that an Identity Provider (Microsoft Entra ID, Okta, Zitadel) would make automatically in production.

In production, this form does not exist. Instead, the IdP is configured with the SCIM endpoint URL (POST /api/scim/v2/Users) and a bearer token. Whenever a user is created, updated, or deactivated in the IdP, it automatically pushes the change to the platform — no human interaction needed.

Users provisioned via SCIM get source: "scim" and an external_id matching the IdP's object ID. They do not get a password here — in production they authenticate at the IdP via OIDC/SAML, not with a local password. 

Provisioning (IdP → Platform):
  POST /api/scim/v2/Users
  {
    "schemas": ["urn:ietf:params:scim:schemas:core:2.0:User"],
    "externalId": "azure-abc-123",
    "userName": "new.user",
    "displayName": "New User",
    "emails": [{ "value": "new@example.com", "primary": true }],
    "groups": [
      { "display": "role:editor" },
      { "display": "product:prod_a" },
      { "display": "product:prod_b" },
      { "display": "org:OU-100" },
      { "display": "controllers" }
    ],
    "active": true
  }

Group claim mapping (automatic):
  "role:X"    → sets role = X
  "product:X" → adds X to products list (first = primary)
  "org:X"     → sets org_unit = X
  other       → stored as plain group name

Update (IdP → Platform):
  PATCH /api/scim/v2/Users/:externalId
  {
    "schemas": ["urn:ietf:params:scim:api:messages:2.0:PatchOp"],
    "Operations": [
      { "op": "replace", "path": "displayName", "value": "Updated Name" },
      { "op": "replace", "path": "active", "value": false }
    ]
  }

Deprovision (IdP → Platform):
  DELETE /api/scim/v2/Users/:externalId
  → Soft-delete: sets status = "deprovisioned"
  → User can no longer log in but audit trail is preserved

Architecture Vision

The foundational thinking behind this POC and the platform model it explores.

Core Philosophy

A loosely coupled, event-driven platform model where shared cross-product capabilities are centralized in a platform layer, while individual products remain autonomous, independently deployable, and free to evolve their own internal models.

The Platform Layer

The platform centralizes capabilities that would otherwise be duplicated across products:

Identity & Access
Centralized user lifecycle, SSO, SCIM provisioning, and role-based access across all products.
Master Data & Mappings
Shared entity registry and canonical ID mappings. Each product keeps its own identifiers, the platform bridges them.
Integration Layer
Unified interface toward external domains and source systems (ERP, HR, CRM). Normalizes data into consistent domain models.
Event-Driven APIs
Ingress/egress event bus for asynchronous communication. Products subscribe to domain events rather than calling each other.
Observability & Governance
Shared tracing, audit logging, configuration management, and operational monitoring across the product portfolio.
Shared UX Shell
Injected navigation, inbox, and branding that creates a unified experience across independent product frontends.

Domain-Oriented Integration

The platform acts as a unified interaction layer toward domains such as Finance, HR, and CRM. Data originating from multiple upstream systems is normalized and exposed through consistent domain-oriented models and contracts.

External domains remain systems of record and publish business entities and events into the platform. Products consume these events, maintain their own internal identifiers and relations, and stay decoupled from each other through shared contracts and event-driven communication.

Data flow
ERP / HR / CRM  →  Platform (normalize + route)  →  Product A, Product B, ...
Product A  →  Platform (event bus)  →  Product B

Product Autonomy

Each product in the portfolio is a self-contained unit with its own:

  • Database and data model — no shared schemas between products.
  • Technology stack — free to choose frameworks, languages, and storage.
  • Deployment lifecycle — independent releases, scaling, and versioning.
  • Internal identifiers — products don't need to know each other's IDs. The platform provides entity mapping.

Products communicate exclusively through the platform's event bus and shared contracts — never through direct database access or synchronous inter-product calls.

What This Approach Enables

✔ Strong domain ownership — each team owns its product's data and logic completely.
✔ Scalable integrations — new source systems added at the platform level, not per product.
✔ Loose coupling — products evolve independently without breaking each other.
✔ Easier onboarding — new products integrate via standard event contracts, not custom APIs.
✔ Consistent data handling — cross-domain mappings managed centrally, not scattered across products.
✔ Independent evolution — products and integrations evolve on their own timelines.

POC Scope

This proof of concept implements a vertical slice through the architecture to validate the model end-to-end:

  • 7 Docker containers — platform, 2 products, Kafka (Redpanda), console, Jaeger, ERP mock.
  • Event-driven data flow — ERP publishes projects/accounts → platform routes to products via Kafka.
  • Shared shell — injected header with navigation, inbox, and pin/unpin across all products.
  • SCIM provisioning — automated user lifecycle from IdP with group-to-role mapping.
  • Budget workflow — full create → edit → submit → publish → cross-product sync lifecycle.
  • Process management — assignment matrix, task inbox, status tracking.
  • External tools — configurable third-party links in the unified navigation.

Production Notes

Shortcuts taken in this POC and considerations for a real deployment.

Multi-tenancy

POC: Single-tenant — one database, one Kafka cluster, no tenant isolation.

Production approach: The platform layer (shell, router, SCIM gateway) can be shared across tenants since it's largely stateless. Key requirements:

  • Tenant-ID propagation — every request carries a tenant identifier (JWT claim or header), validated at the gateway. Misssing this on a single query = data leak.
  • Kafka topic isolation — prefix all topics with tenant ID (tenant-a.projects.in) and enforce ACLs so consumers only read their own topics.
  • Config DB — shared database with a tenant_id column + Row-Level Security (Postgres RLS) so the app can never accidentally cross tenants.
  • Product instances — always per-tenant (separate pods/DBs). This is already how the POC works with isolated containers.
  • Dedicated tenant option — some customers (banking, healthcare) require fully isolated infrastructure. Support this as a deployment variant using the same codebase.

Authentication & Authorization

POC: Simplified login with plaintext passwords in SQLite. SCIM provisioning works but tokens aren't validated cryptographically.

  • Real SSO — OpenID Connect with the customer's IdP (Entra ID, Okta, etc.). Platform issues a signed JWT after IdP authentication.
  • Token validation — products validate JWT signature via JWKS endpoint. No shared secrets in environment variables.
  • SCIM bearer tokens — should be rotatable, scoped per tenant, stored hashed.
  • Session management — token refresh, expiry handling, secure cookie flags (HttpOnly, SameSite, Secure).
  • RBAC enforcement — the POC has roles but doesn't enforce them in product APIs. Production needs middleware that checks role claims on every endpoint.

Data & Event Pipeline

POC: Redpanda single-node, no replication, no persistence across restarts. Events are JSON with basic schema.

  • Schema registry — enforce event schemas (Avro/Protobuf) so producers can't send malformed data. Breaking changes require schema evolution.
  • Dead letter queues — failed events should go to a DLQ for inspection, not be silently dropped.
  • Delivery guarantees — the POC uses at-least-once with idempotency keys. Production should formalize this with transactional producers and exactly-once semantics where critical.
  • Backpressure & rate limiting — protect downstream products from event floods (noisy neighbor problem).
  • Event versioning — events need a version field and consumers must handle old versions gracefully.

Shell & Micro-frontend Architecture

POC: Shell injected via <script> tag. Products are separate HTML apps loaded in full-page navigations.

  • Module federation — consider Webpack Module Federation or import maps for seamless product loading without full-page reloads.
  • Shell versioning — the CDN-served shell.js needs cache-busting and rollback capability. A broken shell breaks all products.
  • CSS isolation — shadow DOM or strict naming conventions to prevent style leaks between products and shell.
  • Cross-product communication — the POC uses page navigation. Production may need a lightweight event bus (postMessage / custom events) for in-page coordination.
  • Performance — shell.js should be < 20KB gzipped. Currently it's small, but monitor as features grow.

Infrastructure & Operations

POC: Docker Compose on a single machine. SQLite in-memory databases. No monitoring, no backups, no TLS.

  • Orchestration — Kubernetes with Helm charts per product. Platform services as a shared namespace, product instances as tenant-scoped namespaces.
  • Database — PostgreSQL (or managed equivalent) with connection pooling, backups, and point-in-time recovery.
  • TLS everywhere — not just ingress; mTLS between services (service mesh like Istio or Linkerd).
  • Observability — the POC has Jaeger for tracing. Add structured logging (ELK/Loki), metrics (Prometheus/Grafana), and alerting.
  • Audit logging — who changed what, when. Required for compliance. Per-tenant audit streams.
  • Secrets management — Vault or cloud KMS for API keys, DB credentials, encryption keys. Not environment variables.

Data Privacy & Compliance

POC: No encryption at rest, no data classification, no retention policies.

  • Encryption at rest — all databases and Kafka logs encrypted. Per-tenant keys (envelope encryption) so one key compromise doesn't affect all tenants.
  • GDPR — right to deletion, data portability, consent tracking. Platform needs a "delete tenant" operation that cascades across all products.
  • Data residency — some customers require data in specific regions. Multi-region deployment support.
  • PII handling — user data (names, emails) must be identified and treated differently from operational data. Minimize PII in event payloads.

Platform Admin: Customer vs Operations

POC: All administration in a single portal. No separation between what the customer's admin does and what the vendor's operations team does.

Production approach: Two distinct admin experiences, potentially role-gated within the same app or as separate portals:

Tenant Admin (customer) Ops Portal (vendor)
Who Customer's own admins Internal operations / SRE team
Scope External tools, users & roles, branding, notifications Tenant provisioning, product setup, data routes, Kafka topics, monitoring
POC tabs External Tools, Identity & Access Initial Setup, Data Operations, Operations, Events
Access Normal login with admin role Separate portal, VPN/IP-restricted, or super-admin role

Implementation options:

  • Role-gated tabs — same admin app, but tabs/sections shown based on role claims. Simplest to build and maintain.
  • Separate portals — distinct deployments for customer admin vs ops. Better security boundary but more to maintain.
  • Hybrid — single codebase, ops-portal deployed on internal network with elevated role scope.

Product Configuration via Platform

Today: Products are configured via YAML files deployed alongside the application. Changing a setting requires a code change, PR, and redeploy.

Opportunity: The platform can serve as a central configuration plane for "moving parts" — settings that change more often than code deploys.

Candidates for platform-managed config:

  • Feature flags — toggle features per tenant without redeploying the product.
  • Display settings — currency format, decimal precision, fiscal year start, language.
  • Data mapping rules — which ERP fields map to which product fields. Already partially in the platform router.
  • Notification templates — email/in-app notification content and triggers.
  • Workflow rules — approval thresholds, budget lock dates, submission deadlines.
  • Integration credentials — API keys for external systems (stored encrypted).

Should stay in YAML / code:

  • Schema definitions — database migrations, event schemas. Too risky to change at runtime.
  • Infrastructure config — resource limits, replica counts, network policies. Managed by IaC (Terraform/Helm).
  • Security policies — CORS origins, CSP headers, auth providers. Change requires deliberate review.

Architecture pattern:

  • Platform exposes a Config API — products fetch their config at startup and poll/subscribe for changes.
  • Config hierarchy — defaults → product-level → tenant-level overrides. Tenant admin can change their tier, ops can change defaults.
  • Audit trail — every config change logged with who, when, old value, new value.
  • Validation — platform validates config against a product-defined JSON schema before accepting changes. Prevents broken configs.
  • Rollback — config versioned so any change can be instantly reverted.

What This POC Validates

  • Shared shell pattern — injected header with navigation, inbox, and pin/unpin works well across independent products.
  • Event-driven data routing — ERP data flows through the platform to multiple products via Kafka with canonical mapping.
  • SCIM provisioning — automated user lifecycle from IdP, including group-to-role mapping.
  • Product independence — each product has its own tech stack, database, and deployment. The platform doesn't dictate internals.
  • External tools integration — lightweight linking to third-party tools in the unified navigation.
  • Admin as a product — platform administration through the same UX patterns as any other product.
