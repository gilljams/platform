Create Budget Project

ℹ️ Show explanation ▸
ℹ️ What happens?
Here you create a budget project that only exists in Product A. The project is automatically registered in the platform and becomes visible to other products (e.g. Product B) without them needing to know where it came from.
⚙️ Technical flow
1. POST /api/projects → Product A creates project locally (SQLite)
2. Publishes BudgetProjectCreated → Kafka topic: product-a.events
3. Platform consumes → creates canonical_id (platform-XXX) in mapper (SQLite)
4. Platform publishes enriched event → Kafka topic: platform.projects.out
5. Product B consumes from platform.projects.out → stores in its read model

Technologies: Express, KafkaJS (Redpanda), better-sqlite3

Resilience & Event Sourcing

ℹ️ Show explanation ▸
ℹ️ What happens if a product goes down?
If Product B (Analytics) is temporarily down, no data is lost. All events are stored in the queue and wait. When Product B starts again it automatically catches up on everything it missed — without you needing to do anything.
⚙️ Technical: Kafka offset & catch-up
Each Kafka consumer has a consumer group with saved offsets.
When a consumer (e.g. product-b) crashes or stops:

1. New events continue to be written to topics by Platform
2. The consumer group's offset remains at the last committed position
3. On restart: consumer resumes from saved offset → processes everything it missed
4. At-least-once delivery: events may arrive twice → idempotent handling required

Demo command:
  docker compose stop product-b    # simulate crash
  # ... publish data via ERP / Product A ...
  docker compose start product-b   # catch-up happens automatically

Redpanda retention: default 7 days → events persist for a long time

What happens?
Edit the budget directly in the grid. When you save, it is stored as a draft locally in Product A — no other product can see it yet. Open Admin from the menu to submit the budget to the platform.
⚙️ Technical flow
Save (draft):
  POST /api/budget → Product A saves lines locally (SQLite)
  No Kafka publishing — data stays in Product A

Submit:
  POST /api/budget-versions/:id/submit
  1. Status changes draft → submitted
  2. Publishes BudgetSubmitted → Kafka topic: product-a.events
  3. Platform consumes → looks up canonical_id via prod_a_id
  4. Platform publishes enriched event → Kafka topic: platform.budget.out
  5. Product B consumes → stores in its read model → shows budget vs actuals
