In production, this transformation happens in the platform backend — not in the ERP. We show it here side by side to illustrate what the adapter does.

1. Dimension Entity — Account

ERP Account
{
  code: "4010",
  name: "Salaries",
  parent: "40",
  type: "leaf"
}
→
econ_entities + econ_relations + econ_entity_attributes
econ_entities:
  dimension: "account", code: "4010",
  name: "Salaries", type: "leaf",
  source_system: "erp"

econ_relations:
  dimension: "account",
  child_code: "4010" → parent_code: "40",
  hierarchy_name: "standard", level: 3

econ_entity_attributes:
  code: "4010",
  account_group: "40"  (derived: first 2 chars)
  debit_credit: "debit"  (derived: 3xxx=credit, else debit)

2. Hierarchy — Organization

ERP Org Units (flat + parent ref)
[
  { code: "OU-300", name: "IT", parent: "DEPT-B" },
  { code: "DEPT-B", name: "Operations", parent: "ACME" },
  { code: "ACME",   name: "Acme Inc", parent: null }
]
→
econ_relations (hierarchy_name='standard')
econ_relations:
  { child: "OU-300",  parent: "DEPT-B", level: 3 }
  { child: "DEPT-B", parent: "ACME",   level: 2 }
  { child: "ACME",   parent: null,     level: 1 } (root)

→ Builds into navigable tree structure
→ Supports alternative hierarchies (hierarchy_name)
→ Identity resolution via relation_type='same_as'

3. Flex-dimension → Dim-slot routing

ERP Routing Fields
ERP GL entries contain these fields:
  activity:     AKT-100, AKT-200, AKT-300
  cost_bearer:  KB-500, KB-600
  counterpart:  MP-200, MP-300

These fields are ERP-specific — other systems
may use entirely different names for the same concepts.
→
dim_routing + dim_models (plattformen)
dim_routing (source='erp', target='prod_b'):
  activity     → dim1
  cost_bearer  → dim2
  counterpart  → dim3

dim_models (product='prod_b'):
  dim1 = "Activity"
  dim2 = "Cost Center"
  dim3 = "Counterpart"

→ The platform translates ERP fields into generic
  dim-slots that all products understand.
